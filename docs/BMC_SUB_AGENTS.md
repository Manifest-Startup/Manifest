# BMC Per-Section Sub-Agents

Each of the nine Business Model Canvas sections is generated by its
own sub-agent (`agent_kind = bmc_<section_name>`). Coexists with the
legacy monolithic `business_model_canvas_service.py`, which still
backs the bulk-generated `business_model_canvas` field on the Idea
type for older UI paths. Per-section panels read from this service.

This is Phase 2a of the agentic-automation roadmap.

## What's in

- `business_model_canvas_sections` table
  ([migration](../supabase/migrations/20260522120000_business_model_canvas_sections.sql)):
  one row per `(idea_id, section_name)` with the latest generated
  content, `needs_user_review` flag, and `generated_by_run_id` linking
  back to `agent_runs`.
- Prompt template
  [`bmc_section.mcp.json`](../backend/app/prompts/bmc_section.mcp.json)
  with strict-JSON output and explicit siblings-as-context framing.
- Orchestrator
  [`backend/app/services/bmc_orchestrator_service.py`](../backend/app/services/bmc_orchestrator_service.py):
  `regenerate_section`, `regenerate_all_sections`, `get_sections`.
  Each regeneration opens a cost-tracked `agent_run`, logs a cost
  event via `llm_usage_tap`, upserts the section row, and closes
  the run. `regenerate_all_sections` continues past per-section
  failures so one transient LLM hiccup doesn't kill the whole canvas.
- GraphQL surface
  ([`schema.py`](../backend/app/graphql/schema.py)):
  - `bmcSections(ideaId)` — returns 9 sections in canonical order,
    placeholders included.
  - `regenerateBmcSection(ideaId, sectionName)` — one section.
  - `regenerateAllBmcSections(ideaId)` — all 9 sequentially.
  - All gated on `ideas.read` / `ideas.write` via the default-deny
    extension's `FIELD_PERMISSIONS`.
- Frontend panel
  [`BmcSectionsPanel.tsx`](../frontend/src/features/ideas/components/BmcSectionsPanel.tsx)
  rendering the nine cards in canonical order, per-section
  "Regenerate" buttons, a "needs review" badge, and a top-level
  "Regenerate all 9" CTA.

## Canonical section order

`bmc_orchestrator_service.SECTION_NAMES` is the single source of
truth. Order matters: `regenerate_all_sections` runs sequentially in
this order so later sections see earlier ones as sibling context.

```
1. customer_segments
2. value_propositions
3. channels
4. customer_relationships
5. revenue_streams
6. key_resources
7. key_activities
8. key_partners
9. cost_structure
```

This is the standard BMC reading flow (right-to-left across the
canvas): nail down WHO first, then WHAT, then HOW, then COST. Putting
customer + value at the top means every downstream section is
generated with explicit customer context in its prompt.

## How siblings improve consistency

When regenerating section N, the orchestrator pulls every other
already-generated section's content and threads it into the prompt
under the `SIBLING SECTIONS` block. The LLM is instructed to keep its
output consistent with those siblings — e.g. if `customer_segments`
identifies "indie game devs", `value_propositions` will speak to
indie game devs rather than picking a different segment.

This is why `regenerate_all_sections` runs sequentially rather than
in parallel. A 2× speedup from parallelism would cost consistency,
and consistency is the whole point of the per-section split.

## Cost tracking

Every regeneration opens an `agent_run` with `agent_kind =
bmc_<section_name>`. The LLM call writes its token usage to
`llm_usage_tap`, and the orchestrator pops + logs it as one
`agent_cost_events` row. So:

- 1 section regeneration = 1 agent_run + 1 cost event.
- `regenerate_all_sections` = 9 runs + 9 events (assuming no failures).

The user-facing billing dashboard already surfaces these
automatically because the per-agent breakdown groups by
`agent_kind`. No additional wiring needed.

## Tests

[`backend/tests/test_bmc_orchestrator.py`](../backend/tests/test_bmc_orchestrator.py)
covers: section-name validation, idea-without-description rejection,
unavailable AI layer rejection, placeholder-row generation, canonical
ordering, happy-path persistence + cost logging + run closure,
`needs_user_review` flag propagation, LLM failure → run marked
failed, empty LLM content rejection, siblings appearing in the prompt
on subsequent calls, full canvas regeneration, and continue-on-failure
behavior during `regenerate_all_sections`.

## What this enables next

- **Bulk regeneration after qualification.** When a qualification
  session completes, the orchestrator could be invoked automatically
  to seed the canvas from the qualified inputs.
- **User-editable sections with diff highlighting.** The
  `last_user_edit_at` column is already there; future UI can show
  "your edits since AI last touched this" inline.
- **Section-level approvals.** The `needs_user_review` flag flips the
  card to a confirm-or-edit state before downstream agents (pitch
  deck, PRD) consume the content.
