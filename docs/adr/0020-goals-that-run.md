# 0020. Goals that run: a plan, an approval, Open Media, and what was learned

- Status: Proposed (2026-11-22).
- Code: `backend/app/services/goals/`, erasure in `services/compliance/tenant_purge.py`, (`store`, `capabilities`, `policy`, `knowledge`, `engine`), `backend/app/graphql/resolvers/goals.py`, `types/goals.py`; resume triggers in `services/integrations/open_media/webhooks.py` (`_wake_goals`) and `workers/generation_worker.py` (`_sweep_goals`); schema `supabase/migrations/20261122120000_goals_tasks_approvals.sql`; voice `services/voice/live/bot.py` (prompt) and `tools.py` (core tools); plugin `agent-plugin/skills/manifest-goals/`; tests `backend/tests/test_goals.py`.

## Context

Manifest could research, draft and talk, but nothing it did outlived a request. Goals lived only in prompts. Messages went out through `sendMessage` / `replyInInbox`, which no catalog rule marked as needing confirmation, so any agent holding the person's token could send. The voice and MCP `confirm` handshake is a client convention; the server never checked it. Nothing recorded what was learned, where it came from, or how sure Manifest was (audit: `docs/MANIFEST_SPEC_STATUS.md`).

## Decision

- **A goal is a row, and its plan is rows.** `goals` holds the outcome and success criteria. `goal_tasks` holds the steps, with `depends_on`, a risk tier, input, result, verification, attempts and the next check time, using the master spec's statuses (`proposed` … `cancelled`). Ideas stay the project entity; a goal may point at one.
- **Capabilities are code, not model judgement.** Each step type (`contact.resolve`, `message.prepare`, `message.send`, `reply.await`, `knowledge.record`) declares its tier, required inputs, and how its result is verified. A step is completed only when its verification passes; for example, a sent message must be found again in the Open Media conversation. Plans come from the person's agent or voice (`createGoal`) or from a template (`startOutreachGoal`), and are validated: no unknown capability, no forward dependency, and no reference to a step the step doesn't depend on. No server-side LLM is needed (bring your own key, ADR 0018).
- **Approvals are enforced where a step runs.** A tier 2 or higher step creates an `approval_requests` row holding the exact `scope` (action, channel, recipient, body, idea) and its SHA-256. `decideApproval` must quote that hash, so the decider saw that exact version. Before running, the step recomputes the scope and runs only if an approved, unexpired approval has the same hash. If the message changed after approval, the step asks again. `decideApproval` and `cancelGoal` are also destructive in the catalog (`confirm: true` in voice, MCP and the CLI). There are no standing authorizations yet.
- **Open Media stays the communication arm.** Manifest uses Open Media's existing API: the public profile lookup, the existing direct conversation (tagged `context.app = manifest`), and the idempotent send (`client_id` = task id, so a retry or crash recovery can't send twice). Open Media has no drafts API, so the prepared message lives in the `message.prepare` step and in the approval. Adding Open Media drafts is a follow-up in that repo.
- **Durable and resumable without new infrastructure.** `advance` is the only thing that runs steps. It is idempotent, and every state change is a compare-and-swap. Three triggers call it: requests, Open Media's signed `message.created` webhook (wakes goals waiting on that conversation), and a sweep in the existing in-process worker every `GOAL_SWEEP_SECONDS` (default 60). The sweep resumes due waits and retries and returns steps a crash left `running` to `ready`. Transient Open Media errors retry three times (1, 5, 30 min); an unlinked account blocks with a clear ask; nothing is hidden.
- **Knowledge has provenance and a kind that fixes its confidence.** `knowledge_facts` stores subject, predicate and value, plus source type, source ref, extraction method and status. The kind (`stated_by_user` 1.0, `verified` 0.9, `external_claim` 0.5, `inferred` 0.3) is assigned by code. A reply is an `external_claim`, never a requirement. A correction supersedes the earlier facts and keeps them.
- **External text is data.** Reply text is stored verbatim, fenced with `ai_safety.wrap_untrusted` before it reaches a model, and checked with `looks_like_injection_attempt`. A suspicious reply adds a `security.untrusted_instructions` event. Nothing in a reply can create, approve or run a step.
- **One event log, one timeline.** `goal_events` (deduplicated by key) records `goal.created`, `approval.*`, `task.*`, `knowledge.*`, `outcome.verified` and security events. `goal.timeline` and `report` (completed, in progress, waiting, needs you, next) are read from it and from the tasks.

## Consequences

- The migration must be applied before the fields work in production. Until then they fail with a missing-table error. The migration is additive.
- On Render's free plan the in-process sweep runs only while the service is awake. Webhooks wake it for replies, and the 10-minute edge keep-alive keeps it mostly warm. Long waits are checked when it next runs.
- Voice sees `goals`, `start_outreach_goal` and `decide_approval` on every turn (27 per-turn tools, up from 24).
- Not yet: standing authorizations, intent classification beyond the voice prompt, meeting scheduling, Open Media drafts and delivery status, email as a channel, a Goals view in the web app, and retention or data-export controls for `knowledge_facts`. Account erasure (`compliance/tenant_purge.py`) deletes all five tables.
